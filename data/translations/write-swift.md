## 初步反应

当该技能首次被无特定问题使用时，只需回答：

>我准备好帮你写现代Swift，按照这门语言想要的方式写。

在用户提问之前，不要提供任何其他信息。

如何按照语言想要的方式编写 Swift，支援至 Swift 6.4。

**工具链基线：Swift 6.3**（截至2026年8月的最新版本）。这里的所有内容都是基于6.3编译的，除非标记⚠了，标记为未发布的Swift 6.4功能。并发指导假设Swift 6.2模型——如果项目运行在6.1或更早版本，则第3节关于“异步”和“@concurrent”的规则不适用。

主线是：**Swift是一种进步的披露语言。从最简单、最静态、最单线程且有效的方法开始，购买动态性——并发、引用语义、存在性、不安全指针——只在你能指出原因的地方。** 以下每条规则都是基于此的应用。

模拟这种违约层级。只有在你能说明理由的情况下，才会往下走一级：

|需要 |伸手去 |只有在 |
|------------ |----------------------- |---------------------------------------------------------- |
|数据 |'struct' / 'enum' |你需要身份、共享或继承 |
|抽象 |混凝土类型 |你有跨类型重复的代码 |
|多态性 |“some P”（通用） |你需要异构存储→“任意P”|
|处决 |主角，同步 |分析显示“异步”→“卡住”→“@concurrent”→“演员”|
|记忆 |“数组”，“字符串” |“InlineArray”、“Span” |→
|安全 |安全API |C 互操作或测量的热路径→“不安全*” |

## 1.具有价值类型的模型数据

值类型是Swift的默认设置，不是特殊情况。

- **默认为“struct”和“enum”。“类”只用于身份、共享可变状态、继承或资源寿命。** 窗口、数据库连接、存储在渲染引擎中的实体——这些都有身份。“点”、“饮料”、“物质”则不然。
- **'let'默认;“var”只有在你变异时才用。** 这和“some”在“any”之前、value在指称之前是一样的纪律：从狭义开始，因由扩大。
- **具有可变引用类型属性的结构既不是值也不是引用。** 复制品共享对象;突变会在复制体中泄漏。要么保持引用的类型不可变，要么只暴露计算过的属性并转发给它，要么将其设为“私有”存储属性，隐藏在写入时复制后面。
- **写时复制是获得非行存储_和_值语义的方式。** 在变异之前，将最后一个类包裹在结构体中，并在变异前检查“isKnownUniquelyReferenced（&storage）”;如果不是，先复制。这正是“数组”、“字符串”和“字典”的工作原理。
- **枚举是“固定集合”和互斥状态的工具。** 用一个“枚举状态”替换一堆可选存储属性（'isSharing'、'selectedRows'、'shareTarget'）会使无效组合无法表示，状态变更变成原子化的，而不是一连串属性写入，容易忘记完成。
- **组合值会产生一个值。** 一个存储属性全部为值类型的结构体，拥有免费的值语义——这使撤销、差分和状态恢复成为一条代码路径，而非每个属性一条。

```swift
struct Material {                       // value semantics preserved
  var roughness: Double
  private var _texture: Texture         // a class

  var color: Color {
    get { _texture.color }
    set {
      if !isKnownUniquelyReferenced(&_texture) { _texture = Texture(copying: _texture) }
      _texture.color = newValue
    }
  }
}
```

**不可复制类型**（“~可复制”）表达唯一所有权：文件描述符、银行转账、开放资源。抑制复制会将“你不能重复运行此事”从断言变成编译错误，使结构体上的“deinit”变得有意义。标记收尾方法为“消耗”，这样编译器才能证明这是最后一次使用。参数所有权变得明确：“借用”（默认只读“）、”消耗“（夺走它）、”输入“/”变异“（临时写入访问）。

## 2.错误与可选——让故障路径可见

快速错误处理基于三点：错误来源被标记，防止它们突然出现;错误包含足够的上下文以便采取行动;而且**可恢复错误与程序员错误**不同。

- **可回收→“投掷”。程序员错误→“precondition”/“fatalError”。** 网络调用失败后程序继续运行。超出范围索引意味着代码错误，必须在漏洞成为安全问题之前停止。
- **带有相关取值的枚举产生最佳错误类型。** 'case duplicateFriend（String）' 胜过 'case duplicateFriend' — 上下文才是关键。
- **“guard”表示错误条件**，因为它强制输出路径。“如果让”用于普通的拆开。
- **类型抛出（“throws（MyError）”）用于内部函数、错误转发通用代码以及受限环境**，在这些情况下，“任意错误”的封装成本过高。对于公共API，未类型“throws”保留了你以后更改错误类型的自由。注意统一：'throws' 是'throws（任意错误）'，non throwing 是'throws（Never）'——这正是让'映射'抽象于两者之间的原因。
- **只在可以陈述不变量**的地方强制展开，并且更倾向于失败的“#require”/“前提条件”带消息，而不是裸露的“！”。

## 3.并发：保持单线程，直到分析另有指示

这是代理最常犯错的部分，因为模型在Swift 6.2中已经改变了。

把所有应用都从主线开始。单线程代码效果很好，大多数应用也不需要离开单线程代码。

**按顺序进行。不要跳过步骤。**

1. **主actor是单线程。**完全没有并发。大多数应用都没问题。
2. **'异步'/'等待'**以隐藏延迟（网络，磁盘）。你自己也没有并发——像“URLSession.data（from：）'这样的SDK API会代为卸载。
3. **'@concurrent'** 将_你_昂贵的作品从主线索中移除——只有在Instruments显示挂机后才可进行。
4. **'actor'** 用来将 _state_ 从主 actor 移开——只有当主 actor 状态过多导致任务不断跳回时才会这样做。

**先打开正确的构建设置。** 在每个项目中启用**可接近的并发**。对于应用模块和面向 UI 的模块，也要将 **Default Actor Isolation** 设置为 **MainActor**——这是 Xcode 26 新应用项目的默认设置，并且会删除大部分“@MainActor”注释。在一个包中：'swiftSettings： [.defaultIsolation（MainActor.self）]'。**不要默认为通用库设置主演员** — 库应提供“非隔离”API，并让客户端决定工作运行位置。

### 规则改变了

**在Swift 6.2中，标记函数为“异步”并不会让它离开当前actor。**它运行在被调用的来源。这正是“最自然编写代码”默认为无数据种族的原因。

- **'@concurrent'** — 总是切换到并发线程池。用它来做你那些CPU密集型的工作。
- **'非孤立'** — 无论其来源何处。**这是库API的正确默认**，因为调用者自己决定。类型上的“nonisolated”使得其所有成员都非孤立（Swift 6.1+）。
- 都不是——都停留在来电者的演员位置。

```swift
nonisolated struct PhotoProcessor {          // decoupled from the main actor
  @concurrent                                // guaranteed to run in the background
  func process(_ data: Data) async -> ProcessedPhoto {
    async let sticker = extractSticker(data)  // two independent jobs, in parallel
    async let colors  = extractColors(data)
    return await ProcessedPhoto(sticker: sticker, colors: colors)
  }
}
```

- **卸载前先做分析。** 使用仪器（时间分析器，挂机）。如果代码能在没有并发的情况下更快，务必先做这件事。并发有实际成本——任务分配、调度和推理。
- **不要为琐碎工作生成任务。** 读取“UserDefaults”值的子任务成本高于保存。
- **每个端到端操作一个任务。**必须按顺序完成的工作归入_一个_任务;独立操作会分配不同的任务，这样运行时可以交错使用。
- **'await'是一个暂停点，它破坏了原子性。** 状态在暂停期间会发生变化，你可以在另一个线程上继续。每次“等待”后重新检查假设。绝不要用锁在一边。切勿依赖线程本地存储。

### 演员重返

行为者保证的是相互排斥，而不是交易。在同一演员身上有两个“等待”，其他工作都在进行。

- **在同步方法中变异演员状态。** 演员上的同步代码会不间断地运行到完成——这就是你的事务边界。
- **保持异步演员方法的薄，由同步事务操作组成，并在每个“等待”时保持演员一致的状态。
- 经典的bug：检查缓存→“wait”下载→写缓存。两个任务都没完成，两个任务都下载，第二个任务把第一个任务打得更惨。在“等待”结束后重新检查，或者取消飞行中的工作。
- **演员不是先入先出（FIFO）。** 他们优先运行最高优先级的工作，正是为了避免优先级反转。如果需要排序，可以用任务（从头到尾运行）或者“异步流”，而不是演员。

## 4.可发送与共享数据

“可发送”标记为安全可跨隔离域共享的类型。编译器会在每个任务和演员边界处检查它。

- **值类型在存储时为“可发送”——非公开类型自动推断。**公共类型从未被推断出可发送性**：标记公共类型为“可发送”是对客户的承诺，所以Swift让你写出来。
- **actor 和 '@MainActor' 类隐含为“可发送”**，因为它们的状态是孤立的。
- **大多数模型类既不应该是“@MainActor”也不是“可发送”。** 故意保持非“可发送”——这样可以防止模型一半在主线程中变异，而另一半在后台被变异。如果需要离开主角，就让他们“非孤立”，而不是“可发送”。
- **只要发送方停止使用，你仍然可以在域间_发送_非“可发送”对象。在交接之前，先完成所有突变;之后再碰它才是错误。
- 闭包也捕获状态。只有当函数类型确实跨域时，才标记为“@Sendable”。
- **'@unchecked Sendable' 是编译器无法检查的承诺。** 保留给具有真实内部同步的类型（如“Mutex”，锁）。全球地图上的“非隔离（不安全）”也是一样——最后手段，不是警告消音器。

**当你遇到数据种族错误时，往下查这个列表：**

1. **不要共享它。** 将共享对象迁移到本地，这样每个并发作业都有自己的实例。（这是大多数真实错误的修复方法。）
2. **把它设为“可发送”值类型**，所以“共享”其实就是复制。
3. **将其定位到一个演员**——主角，或你自己的演员。
4. 只有在“同步”模块中（存储在“let”属性中）或“可发送”（@unchecked Sendable）中，才可以访问“Mutex”/“Atomic”。

**全局和静态变量是最常见的错误来源。** 按偏好顺序：设为“let”;放到“@MainActor”;用“变异材料”包裹;“非隔离（不安全）”。注意 Swift 中的全局初始化是懒惰的 _ 和 原子式的——这与 C 不同。

**桥接旧回调API：**如果你拥有代理协议，请用“@MainActor”来注释。如果没有，标记方法为“nonisolated”，并使用 “MainActor.assumeIsolated { }”——它断言而非跳跃，因此捕获声音大，而不是静音奔跑。合规上的“@preconcurrency”是同一意思的简写。使用“@preconcurrency导入”功能暂时静音尚未迁移的模块的可发送性警告;一旦出现，警告就会正确地回来。

## 5.结构化并发

总是偏好有结构的任务。

结构化任务（“异步let”、任务组）的作用域类似于局部变量：它们不能超过区块，自动等待，并且通过任务树继承了取消值、优先级值和任务本地值。非结构化任务（'任务 { }'， 'Task.detached'）会自动不会给你这些。

- **'async let'** 表示固定且静态已知的并发子节点数量。
- **'withTaskGroup'** 当数字是动态的。任务组遵循“异步序列”——在交付时迭代结果。当子节点没有返回任何信息时，使用 **'withDiscardingTaskGroup'**：它会立即释放每个子节点的资源，并在第一次错误时取消兄弟姐妹。
- **'任务 { }'** 仅在工作生命周期不符合范围时进行——响应代表回呼、按钮点击、视图出现。它继承了演员的隔离性和优先级;你必须自己管理取消。
- **'任务.分离'** 几乎从不。它什么都不继承——无论是隔离、优先级还是任务本地。如果你需要一个分离根，可以在里面放任务组 _ 而不是反复分离。

**取消是合作的。**取消会触发标志;它什么都阻止不了。在开始昂贵工作之前，检查“Task.isCancelled”或“try Task.checkCancellation（）”，并且在同步辅助工具中也要检查。对于暂停而非运行的工作（如“AsyncSequence”的“next（）”），可以使用“withTaskCancellationHandler”——请记住，处理程序是立即且同时运行的，因此它接触的状态需要真正的同步（原子或锁，而非actor——你无法保证actor的顺序）。

**绑定你的并发。** 不要在无界列表中每个项目只分散一个子节点。先有N个孩子，每完成一个就再添加一个。

**任务本地值**（“@TaskLocal”）在任务树中传播上下文——请求ID、轨迹跨度——而无需在每个签名中穿插参数。把它们设为可选，这样未绑定的读取就有合理的默认值。

**桥接回电：** “withCheckedContinuation” / “withCheckedThrowingContinuation”。合同是**在每条路径上只恢复一次**——永不恢复将永远挂断呼叫者;重复比赛两次是致命错误。对于后期触发的代理 API，存储续写，恢复时将其消除。（Swift 6.4 — 未发布 — 增加了一种“续写”类型，可在编译时检查单次恢复。）

**'AsyncSequence':**迭代为“for waitit”/“for try wait”。用“AsyncStream” / “AsyncThrowingStream”来适配现有的基于处理程序或代理的API——在闭包内构建源代码，从处理程序中“yield”，并在“onTermination”中进行清理。

## 6.SwiftUI 中的并发

- **“视图”是“@MainActor”孤立的**，包含的所有内容，包括你的“”@State“，也是孤立的。你几乎不需要在视图或视图模型上写“@MainActor”——而且默认使用主演员时，你可以删除已有的。
- **SwiftUI 故意把你的部分代码从主线程跑掉**以降低帧率。该信号在 API 签名中为 '@Sendable'，包括 'visualEffect'、'Shape.path（in：）'、'Layout' 要求、'onGeometryChange'。当你在这些闭包内部遇到隔离错误时，**不要发送“self”——把你需要的值复制到该闭包的捕获列表中。**

```swift
.visualEffect { [pulse] effect, proxy in    // copy the Bool, don't capture self
  effect.blur(radius: pulse ? 2 : 0)
}
```

- **SwiftUI 的动作回调是有意同步的。** 时间敏感的 UI 更新——即响应手势或滚动事件启动动画——必须在事件同一帧内进行。在同步回调中输入“withAnimation”状态变化;只为后续的长期工作开启“任务”。
- **在UI和异步工作之间的接缝处放置一段状态。**视图启动任务;异步层在完成时会进行同步变异;界面会做出反应。这样可以保持视图逻辑同步，并且可以测试异步逻辑而无需导入SwiftUI。

## 7.协议与通用药

不要从一个课程开始。**也不要从协议开始。**

工作流程：**编写具体类型→注意到它们之间的重复代码，→将共享能力纳入协议→编写通用代码。** 几乎相同的实体过载是该泛化的信号。

- **没有每个类型自定义的协议是浪费协议。** 如果每个一致性都使用相同的默认实现，则应在现有协议上编写受限扩展。复杂的协议层级（“类型动物学”）耗费编译时间和二进制大小，且无需购买任何东西。
- **更倾向于使用has-a而非is-a。** 如果协议的部分操作对你的类型有意义，不要细化它——用通用结构包装，并完全暴露你想要的API。（“GeometricVector<存储：SIMD>”而非“GeometricVector： SIMD”。）
- **协议需求是一个定制点** — 它是动态调度的，符合规范类型的实现在各处都占优。**只有扩展中的方法是静态分派的**，因此conformer的版本_shadows_而非覆盖它，而只知道'任意P'的代码调用扩展的。如果某种类型应该能自定义某些东西，就把它设为必备。
- **重于继承的复合。** 类继承是单一的（一个超类），侵入式（你继承存储的属性和初始化器复杂度），并且留下关于可覆盖哪些内容和何时调用超级的未成文契约。改写小价值。
- **强制下行是一种代码气味**——通常意味着类型关系被类层级或存在性关系丢失。

### “部分”与“任何”

- **默认写成“some P”。当你需要存储任意类型时，可以改成“任意P”。** 和“变量”之前的“let”是同一纪律。
- “some P”——每个作用域一个固定的底层类型。你保留所有类型关系，包括相关类型，编译器可以专门化。
- '任意 P' — 类型擦除框，动态类型在运行时变化。对于异构集合、底层类型的可选性以及完全隐藏抽象来说，是必要的。你为此付出了代价：关联类型的关系被抹除到上限，调用对优化器来说是不透明的。
- **你不能调用一个在“任意P”上取关联类型的方法。** 擦除在产生位置（结果被擦除到上界）时工作，但不在消耗位置工作。解决方法是将存在函数传递到一个取“某个P”的函数中——编译器将其解箱，在该作用域内类型再次被固定。
- **受限存在型和不透明类型** — 'some Collection<Element>'， 'any Collection<any Animal>' — 允许你隐藏'LazyFilterSequence<[Animal]>'，同时仍暴露元素类型。在你自己的协议（“协议容器”）上声明主关联类型<Item>，针对调用者实际提供的类型，而不是像“迭代器”这样的实现细节。
- **“where”条款中的同类型要求**是你确定协议间关系的方式（“whereSelf.CropType.FeedType == Self”）。没有它们，“种植后收获”就无法排版，错误的一致性容易被编译。

## 8.API设计——使用点的清晰度

在使用点上的清晰度是这里最重要的目标。

- **仅限Swift的API中无类型前缀。**模块进行消歧。只有在 API 镜像到 Objective-C 的前缀时才保留。但避免使用具体框架中过于笼统的名称——它们脱离上下文会让人难以理解，还会强制手动消歧义。
- **从异步替代方案及任何直接返回结果的程序中去除前导“get”**。“persistentPosts”，不是“getPersistentPosts”。
- **访问控制是文档。** “private”（文件）、“internal”（模块及默认代码）、“package”、“public”。在边界处显式化正是上述可发送性和API演化决策的关键。
- **设计模型，使非法状态无法拼写。** 私人设定器加上验证变异方法;闭集的枚举;一个强类型“UUID”，而不是“字符串”。
- **属性包装器** 会剔除_access policy_（'@Argument'，'@Published'，防御性复制，懒惰，线程本地），因此声明网站用一个词陈述策略。在关键路径上与“@dynamicMemberLookup”结合，通过包装器投影（这就是“$binding.title”的工作原理）。
- **声明式DSL的结果构建器**。**巨集**当样板是编译器本可以编写的代码时（§12）。

## 9.表现——先测量，然后选择

低等级Swift性能主要由四个成本主导。知道你付的是哪一个。

1. **函数调用**——参数复制、静态与动态派遣、呼叫帧分配和阻塞优化。
2. **内存布局**——在线存储与非在线存储;动态尺寸类型。
3. **分配** — 全局（免费）、堆栈（廉价：一次减法）、堆（昂贵：搜索加锁定）。
4. **复制品**——保留/释放和递归结构副本。

**但先做算法工作。** 每次写循环时，试着用调用算法来替代它。最大的胜利几乎从来不是微观优化：

- **了解你所调用的复杂性。** 'Array.remove（at：）' 是 O（n）;在循环中调用它为 O（n²）。“removeAll（where：）”总共为O（n）。通过每字节重新切片构建“数据”的费用为 O（n²）;“popFirst（）” 是 O（1）。这两者都是100×+回归，隐藏在看起来干净的代码背后。
- **链式“map”/'flatMap'/'filter'为每个阶段分配数组。** 优雅≠快速。如果流水线在热循环中按像素或元素运行，输出大小调整一次并写入。
- **然后进行分析。** Instruments 的时间分析器和分配，运行在 _test_（二次点击测试的运行按钮→配置文件），这样你测量的正是你关心的代码。“platform_memmove”主导火焰图表示意外复制;百万瞬态分配意味着中间阵列;“swift_beginAccess”表示运行时独占性检查;“swift_retain”/“swift_release”表示引用计数流量。

**混凝土杠杆，大致按他们买的东西顺序排列：**

- **“最终”对你不打算子职业的职业**会变成动态调度静态并解锁内联。整体模块优化让编译器在很多情况下帮你证明这一点——并且实现了泛型专用化，也就是泛型不再成本。
- **结构存储是在线的;类存储不合规。** 小型结构体是免费的;一个包含三个引用类型字段的大结构体需要三次保留值_per copy_，而一个类则需要一次保留。如果你经常复制，就用写写复制。
- **任意P存在缓冲区为3字的内联缓冲区。** 适用于在线的值;更大的文件是每份副本分配堆。同样的技巧也适用：给大类型间接存储并采用写时复制，它就能重新进入缓冲区。
- **同质的“[我的模型]”胜过“[任何模型]'****——密集填充，类型信息传递一次，专业化。“[任意型号]”是灵活但不透明的选项;需要的时候拿。
- **将泛参数限制在类（'T： AnyObject'）上，即使没有专门化，编译器也能获得已知的表示。
- **'InlineArray<N， T>'**（Swift 6.2）用于固定大小存储：元素内联存储，类型大小通过值泛型实现，无堆分配，无引用计数，无唯一性或独占性检查。如果被复制或分享，那就是错误的选择。
- **'Span' / 'RawSpan' / 'OutputSpan'**（Swift 6.2）将“withUnsafeBufferPointer”替换为直接访问连续存储。它们是无法逃脱的，所以编译器会把它们的生命周期绑定到容器上——你能获得指针性能而不存在生命周期bug，保留/释放也会消失。
- **将存储的属性从嵌套类移到父结构体**会移除运行时的排他性检查。
- Swift 6.3版本发布时，测量需求为：'@inline（始终）'（方法与'final'配对）和'@specialized（其中 T == ...）'（SE-0460）预先专门化热混凝土类型的通用药。
- 在 Swift 6.4（**未发布**——见 §15 下方注释）中：大容量存储值时用“借用”/“变异”访问器代替“get”/“set”，“UniqueArray”/“UniqueBox”，以及“Ref”/“MutableRef”以从循环中抬起重复查找。

**异步函数**将状态保持在每个任务的板分配器上，而不是C栈，并在每个悬挂点拆分为部分函数。成本结构类似于调用开销略高的同步函数——这也是不要做一个没有等待功能的“异步”功能的原因之一。

**往返主演员的跳跃需要实际的上下文切换。** 批处理：将循环 _into_ 'loadArticles'/'updateUI' 推送，这样它们能接收数组，而不是每次跳两次。

## 10.ARC和对象寿命

- **对象的保证寿命在最后一次使用时结束，而非闭合括号。** 观察到的生命周期是优化器和_will_变化的涌现属性。依赖于“deinit”运行时间的代码是潜在的bug。
- **“弱”/“无主”用于打破引用循环——仅此而已。** 在强所有者最后一次使用后读取“弱”引用，可能合理地判定为“nil”。可选绑定比强制解开还糟：它会把响亮的撞击声变成无声的错误答案。
- **比“弱”更好：不要构建循环。** 将共享数据分解为双方引用的第三种类型，将循环变成树状结构。
- **下一个最佳方案：重新设计API**，使对象只能通过强引用访问。“withExtendedLifetime”虽然有效，但正确性会转移到你身上，并通过代码库传播——把它当作补丁，而不是设计。
- **将“deinit”副作用保持本地化。** 发布指标或从“deinit”序列中发射全局效应以针对优化器决策。在呼叫现场使用“延期”，并保留“deinit”以便验证。
- Xcode 的 **优化对象寿命**构建设置会将观察到的寿命缩短到保证最小值，并会准确地发现这些漏洞。

## 11.测试——默认为快速测试

使用**Swift Testing**进行新检测。XCTest仅仅需要用于三件事：UI自动化（“XCUIApplication”）、性能指标（“XCTMetric”）以及必须用Objective-C编写或捕捉Objective-C异常的测试。

- **'@Test' 在任何函数上** — 全局、静态或实例;“异步”、“投掷”和全局演员隔离均可工作。
- **'#expect（...）' 接受普通表达式。** 没有一类“XCTAssertEqual”式函数需要记忆——如“#expect（a == b）”、“#expect（list.isEmpty）”、“#expect（！x.contains（y））' 在失败时都捕捉并显示子表达式值。
- **'试试 #require（...）'** 在测试失败时停止，并安全地展开可选程序。这替换了“continueAfterFailure = false”，并允许你选择每个预期值。
- **套件是“struct”。每个测试函数都会创建一个新实例，因此状态不会在测试间泄漏。设置时使用“init”;只有在拆解时才用“类”/“演员”。巢穴套装组到组队。
- **参数化代替复制粘贴或循环。** '@Test（参数：[...]）' 独立运行每个案例，并行运行，可单独重跑，失败的参数会在结果中被命名。两个参数集合生成完整的叉积——当你想要匹配的对时，使用“zip（）”。
- ** 特征携带意图：** '.enabled（if：）' / '.disabled（“reason”）'' 表示条件（切勿注释测试——禁用的测试仍会编译），'.bug（url）' 用于追踪，'.tags（...）当测试确实无法并行运行时，用于关联文件和目标间的测试，'.timeLimit'， '.serialized'。使用“@available”而不是运行时的“#available”检查，这样测试库就能知道。
- **'withKnownIssue { }'** 表示测试在你无法控制的部分失败——它会持续编译和运行，并告诉你问题何时修复，不同于 '.disabled'。
- **“确认”**用于触发N次回拨;“withCheckedContinuation”用于一次性回调且无异步超载。
- **测试默认并行运行，顺序随机。** 这是一个特性：它揭示了隐藏的测试间依赖关系。重构而不是直接用“.serialized”。
- **Exit tests** — '#expect（processExitsWith： .failure） { ... }' — 覆盖孤立子进程中的“前提”/“致命错误”路径。仅限macOS、Linux、FreeBSD、Windows。
- 迁移：两个框架共存于一个目标中，因此可以逐步迁移，今天就在Swift Testing中编写新的测试。**测试框架互操作性**（swift-testing ST-0021;请查看你的Xcode版本可用性）允许将包裹“XCTFail”的助手从Swift Testing测试调用，反之亦然;将模式设置为**完成**或**严格**（不是**limited**，也绝不是**none**），这样跨框架问题依然错误，并指向“Issue.record”替换。

## 12.宏量营养素

写代码时要用宏，编译器才能导出——而且只有这样。

- **宏在扩展前会进行类型检查。** 参数会根据宏声明的签名进行检查，因此滥用在调用点是干净的错误，而不是生成代码中的混乱。
- **独立（'#foo'）** 产生表达式或声明。**附加的（'@Foo'）** 在五个角色中补充声明：成员、对等、访问者、成员属性、一致性。角色组合——“@Observable”是成员 + 成员属性 + 一致性。
- **用“assertMacroExpand”测试宏作为纯语法树变换。这是最快的循环，也是避免没人看代码的漏洞的方法。在“扩展”和“po”中设置断点，学习其形状。
- **当宏不适用时，发送真实诊断。** 投出错误，或使用“context.addDiagnostic”表示特定位置的警告和修复。绝不要让宏默默生成无法编译的代码。
- 扩展代码是普通的Swift：可检查（“展开宏”）、可调试、可步进。

## 13.日志与调试

- **“日志器”来自“os”，不是“print”。** 为每个子系统和类别创建一个。消息以优化的形式存储，只有在显示时才会渲染，因此日志保存成本低廉。
- **非数字插值默认被遮蔽。** 仅在非个人数据中选择使用“privacy： .public”的值。当你需要关联值而不暴露它们时，可以使用'.private（mask： .hash）'。
- **层级控制持久性和成本：** “调试”（永不持久，最快——消息结构在非流式时完全被优化消除）、“信息”、“通知”（默认）、“错误”、“故障”（最持久，最慢）。在“错误”/“故障”处记录你在错误报告中需要的内容。
- **记录关联ID**（任务或请求UUID），你可以从设备日志归档中过滤掉整个失败历史，而无需重现。'log collect --device --start ...'，然后在控制台按子系统筛选。
- “format：”和“align：”是免费的——使用它们以便日志可读且可列选择。
- LLDB 理解 Swift 任务：它会跨线程逐步处理“wait”，“swift task info”显示优先级和子任务，命名任务会在调试器和 Instruments 的 Swift 并发模板中显示。

## 14.不安全代码与互操作性

- **“不安全”意味着 API 无法完全验证其输入，因此违反其前提是未定义行为**——但不意味着它会崩溃。安全API故意设陷阱;干净致命的错误才是安全的结果。
- **更倾向于使用“Span”而非“Unsafe*Pointer”。自Swift 6.2起，有一种安全、不可逃逸且同样快速访问连续存储的方法。为C的互操作保留原始指针。
- 如果必须使用指针：尽量保持不安全区域，使用**缓冲**指针（地址+计数）而非裸指针以跟踪边界，绝不让指针逃离其关闭，并运行**地址净化器**。
- 在安全关键模块中启用**严格内存安全**——它强制所有不安全使用在源代码中被确认，这才使审计成为可能。Swift 6.4的“@diagnose”属性（未发布）允许你在单个功能上开启它。
- **互操作是双向且增量的。** C、Objective-C 和 C++ 类型可直接映射到 Swift（包括 C++ 值语义、容器作为 Swift 集合，以及仅移动类型作为“~可复制”）。Swift 6.3 的“@c”属性将 Swift 函数重新暴露到 C（当声明已存在于头部时，使用“@implementation”）。一次只用一个文件来收养Swift;不要重写。

## 16.将现有代码库迁移到 Swift 6

顺序很重要，而混合步骤就是迁移停滞的原因。

1. **先用新编译器构建。** 源代码兼容性意味着这应该能在Swift 5模式下正常工作。
2. **每个目标，启用完全并发检查**（Swift 5模式+所有Swift 6警告）。从**UI/应用层**开始，而不是下面的框架——SDK已经有大量主演员注释，所以修复率很高。
3. **先修复警告，最便宜。** 预计会收到数百个来自少数根源的警告：'var' 全局函数本应是'let'，属于'@MainActor'的自由函数，一个需要'： Sendable'的公共结构。一条线可以清除数十条。
4. **将目标切换到Swift 6语言模式**以锁定作品。
5. **移动到下一个目标，重复。**
6. **之后单独重构。** 绝不要将重大重构与启用数据竞态安全结合——你必须同时放弃两者。

你可以关闭严格检查，然后转运;你所做的每一次修复都是真正的改进，并且得以保留。启用**可接近的并发**，对于应用模块，默认在启动前先启用主角色——这两者都能显著减少错误数量，Xcode还会自带迁移工具帮你应用许多更改（swift.org/migration）。
